# R09 receipt. Establish strict offline runtime readiness

- Starting commit: `16bbde3` (R08)
- Red proof: `tests/e2e/offline-flow.spec.ts` did not exist. Its first full-flow run failed at intake (runtime not resident); the first run after gating failed at the pdf worker dying across document switches, reproduced deterministically before the fix. `zero-network.spec.ts`'s strict rewrite failed on three separate leaks (editor chunk, flatten chunk, assetFactories chunk) before passing.

## The readiness owner

`src/pdf/runtime.ts` owns preparation and exposes a small state machine: `loading | ready | failed`, with subscribe for React and retry. `ensureRuntimeReady()` resolves only after:

- the data-asset module (CMaps + standard fonts), the editor chunk, the flatten chunk, and the pdf.js auxiliary factories are resident;
- a probe PDF has been parsed on a real worker (the pdf.js worker started, answered, and read resident bytes);
- the resident flatten worker has answered a `ping` handshake.

`App` kicks preparation on mount and renders the state as an accessible status line. Intake is refused until ready — the drop zone declines files with a visible reason, so a user cannot start work the app cannot finish offline. A failed preparation shows its message and a Retry control.

## Zero-fetch pdf.js

- `scripts/generate-asset-module.mjs` commits `src/pdf/generated/pdfAssets.ts`: all 169 CMaps and 16 standard font files from pdfjs-dist as base64 with sha256. `loadDocument` now passes `useWorkerFetch: false` plus custom `CMapReaderFactory`/`StandardFontDataFactory` classes that decode from that table. pdf.js's default factories fetch `/cmaps/` and `/standard_fonts/` at render time — fetches the CSP forbids, which is why CJK-encoded and standard-font PDFs previously could not render offline at all.
- The CMap proof is a real dependency, not a Helvetica fixture: `tests/e2e/helpers/fixtures.ts` builds a Shift-JIS document whose Type0 font encodes with the predefined `90ms-RKSJ-H` CMap. `tests/unit/pdf-assets.test.ts` renders it through the app's factory classes and asserts the factory was consulted for exactly that CMap, plus the refusal path for a CMap outside the bundle. The extracted text is empty because the named font does not exist locally; the CMap resolution is asserted directly rather than through glyphs.

## Worker lifetimes

- **pdf.js**: `loadingTask.destroy()` terminates the worker that served the document — with `GlobalWorkerOptions.workerPort` that is the shared port, so the first document close killed the worker for every later load. Reproduced before the fix: a drag reorder plus a document switch left the editor in the load-error state with no recovery. Each document now gets an isolated worker built from resident bytes — the worker source ships as a committed string (`src/pdf/workerSource.ts`, its own lazy chunk) turned into a blob URL. `worker-src 'self' blob:` already permits this; the script is never fetched.
- **flatten**: one resident worker, started at readiness and reused across batch attempts instead of spawn-per-attempt. Jobs are serialized inside the worker, every response echoes a `jobId`, and callers ignore responses from other attempts. A crashed worker is withdrawn and the next attempt rebuilds one from resident bytes.

## Readiness Retry is a reload

A failed preparation leaves the document poisoned: Chromium caches failed dynamic-import results for the document's lifetime, so an in-place retry of the same modules cannot succeed — verified by watching Retry fail with `Failed to fetch dynamically imported module` until the reload approach landed. Nothing user-facing exists before readiness (intake is gated), so the reload is free. An offline reload remains out of scope (O03) and is not claimed.

## Chunk-budget fight

The initial payload grew three separate times, each caught by `verify:production`'s 300 KiB gate, and each fixed structurally rather than by loosening the gate:

1. The raw worker source merged into the entry chunk — explicit `pdf-worker-source` chunk.
2. `generated/pdfAssets.ts` merged into its importer's chunk — explicit `pdf-assets` chunk.
3. `render.ts` (entry-reachable via the session store → `normalizeSession`) statically imported the asset table — the factories moved to `assetFactories.ts`, loaded dynamically inside `loadDocument`, and added to the readiness preflight.

Final initial payload: **67 KiB gzip JS** (budget 300 KiB). The readiness boundary adds lazy chunks, recorded as the new baseline: pdf-assets 2.62 MB, pdf-worker-source ~1.4 MB, textLayout 1.73 MB, flatten.worker 2.20 MB, pdf-runtime 1.71 MB. These are local-disk loads, not network transfers.

## What the browser proof covers

After the readiness boundary, with the network cut (`context.setOffline(true)`): intake of two PDFs, a typed signature (bundled font), an uploaded signature, placement, an honest autosave status, editing a second document, a single download, apply-to-all, and a batch ZIP download — all succeed offline. Before readiness, blocking the lazy chunks fails preparation visibly and Retry completes it. No request ever touches `/cmaps/` or `/standard_fonts/`. After readiness, first-use signing issues zero requests, as does idle time.

## Deviations

- `zero-network.spec.ts` was rewritten rather than extended: the old blanket exclusions for `/cmaps/`, `/standard_fonts/`, and worker assets are exactly what this task removes. It now asserts those paths are never requested at all and that silence holds after readiness.
- The readiness status line and `intakeDisabled` prop are new UI surface beyond the plan's named files (`App.tsx`, DropZone) — the plan requires the state be "visible and accessible" and intake be gated, which needed a rendered element and a prop.
- `tests/e2e/*` specs gained a shared `waitForRuntimeReady` helper: the gate is the feature, and every intake scenario must cross the boundary.
