## Changes

- `src/lib/imagePolicy.ts` (new): the single source of policy numbers shared by import and upload. `IMPORT_MAX_JSON_BYTES` 64 MiB, `IMPORT_MAX_ASSETS` 1,000, `IMPORT_MAX_DECODED_BYTES` 64 MiB, `IMPORT_MAX_PNG_BYTES` = `UPLOAD_MAX_FILE_BYTES` 10 MiB, `MAX_EDGE_PIXELS` 4,096, `MAX_PIXEL_AREA` 16,000,000. `dimensionsExceedProcessingCaps` rejects; `normalizedUploadDimensions` scales down preserving aspect ratio and never up.
- `src/db/signatures.ts`:
  - `encodeBase64` replaces the `String.fromCharCode(...bytes)` spread with 16 KiB chunks. The spread overflowed the call stack above a few hundred kilobytes, which is review finding 8.
  - `importLibrary` refuses a file above the JSON limit on `file.size` alone, before reading a byte.
  - `validateImportEnvelope` validates and decodes the entire envelope before any write transaction opens, so a failed import leaves every previous record unchanged. It requires nonempty IDs, supported `kind`/`source` enums, finite timestamps, valid base64, positive integer dimensions inside the processing caps, and a decoded PNG whose IHDR agrees with the declared dimensions.
  - Byte ceilings are applied from the base64 length and trailing padding *before* the regex scan and decode. `impliedDecodedBytes` is exact rather than `length * 3 / 4`, because the padding-aware form is what allows a payload of exactly 10 MiB to be accepted.
  - `pngIsComplete` requires the 12-byte IEND trailer. Slicing whole base64 quanta keeps the string valid base64, so a truncated payload previously passed header validation and would have imported as an image that cannot render.
  - Conflicting duplicate IDs inside one file are rejected; identical duplicates are counted as skipped, as are IDs already present.
  - Valid imported PNG bytes are retained exactly. Uploads are re-encoded through the existing canvas path.
  - `markLibraryExportOffered` replaces the watermark write inside `exportLibrary`. The UI calls it only after the browser accepts the download offer, and the label is an export offer, not proof of retention.
  - `bumpAssetsAddedSinceExport(count)` takes a count, so one import performs one read-modify-write instead of one per asset. `getBackupReminderState` fires at 30 days or 10 additions since the watermark; absent fields read as 0 for legacy prefs.
- `src/db/schema.ts`: `Prefs.assetsAddedSinceExport?: number`.
- `src/components/library/canvas.ts`: `imageFileToCanvas` rejects zero natural dimensions and normalizes uploads into the processing caps before allocating a canvas, then drops the decoded image. `ensureFontReady` waits for `document.fonts.load` and verifies the face, recovering with a fresh `FontFace` when the CSS face was poisoned.
- `src/components/library/TypePad.tsx`: preview and save both await `ensureFontReady`. A font that cannot be confirmed shows a retryable failure instead of saving fallback typography, and the font is re-verified at save time.
- `src/components/library/LibraryTray.tsx`: upload limit reads from the shared policy.
- `src/components/library/ImportExport.tsx`: marks the export offered after the click and labels the status accordingly.
- `src/lib/strings.ts`: `import-too-large`, `import-too-many`, `import-conflict`, `fontNotReady`, `retryFont`, and `imports.exportOffered` plus the two reminder messages.

## Font readiness: what the browser actually does

The recovery path was justified by a claim that turned out to be half right, and the verification was wrong in a way that made recovery impossible to observe. Measured in Chromium via `page.evaluate`, not inferred:

- A CSS `@font-face` left in `error` by an aborted fetch **never refetches**. A second `document.fonts.load` rejected without issuing any HTTP request (route log: `["abort","abort"]`, two aborts, none after unblocking). Recovery is genuinely required.
- `new FontFace(name, url)` stores the family name raw, so the resulting face does not match the family the canvas font string asks for, and `document.fonts.check` reports false. Constructing with the quoted name does not help.
- The recovered face **is** used for canvas rendering. Verified by comparing rendered pixels: with recovery, `68px "SignLite Caveat", cursive` renders distinctly from `68px "NoSuchFamilyXYZ", cursive`.
- `document.fonts.check` is the wrong instrument because it consults *every* face matching the family, including the poisoned one. Verification now reads face status across the set, normalizing the quotes the FontFaceSet adds to names containing spaces.

The first probe of canvas behavior was invalid and had to be discarded: it assigned a font shorthand with no size, which is silently ignored, so every comparison compared two blank canvases. The numbers above come from the corrected probe using a valid `68px <stack>` shorthand.

## Deviations

- `src/lib/imagePolicy.ts` was created; the plan anticipated this with "create a small image-validation module if both import and upload need the same policy".
- `tests/e2e/helpers/tmp.ts` was created to write the 64 MiB fixture to disk. Playwright caps in-memory `setInputFiles` buffers at 50 MB.
- `tests/e2e/zz-dbg-font.spec.ts` was deleted. It was an unasserting console-logging probe; its finding is now a real assertion in the delayed-font test, which aborts the font request, requires the save to be refused, then unblocks and requires the retry to produce a genuine preview and a saved asset.
- PNG completeness is verified structurally (magic, IHDR agreement, IEND trailer), not by decoding. Full decode of every imported asset would cost real time on a 1,000-asset envelope. A PNG whose chunks are internally corrupt but whose header and trailer are intact would still import.
- The oversized-PNG and exact-limit unit tests carry explicit 60 s budgets and the 300 KB export round-trip 120 s. These are measured costs of tens of megabytes of base64 in jsdom, roughly 22 s for the 300 KB case alone, not signs of a hang. The default 5 s budget turned them into coin flips under suite contention.

## Measured effect of the ordering fix

`tests/unit/signatures.test.ts` went from 27.3 s with one timeout to 8.9 s once the byte ceilings were applied before the decode, because the oversized-payload case no longer pays for a regex scan and an `atob` over 14 MiB of base64. The same change also turned the exact-limit case from rejected to accepted.

## Not verified here

Peak decoded memory and backup time for the limit fixture were not captured with a profiler, so the chosen 64 MiB decoded and 1,000 asset ceilings rest on reasoning about bounded work rather than a measurement on the intended library fixture. The plan asks for those limits to be verified against that fixture before adoption; that step is still open.
