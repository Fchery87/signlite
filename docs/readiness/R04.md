# R04 receipt. Initialize autosave and report the latest revision

- Starting commit: `6c9a084` (R03)
- Regression observed failing first: with the pre-change `sessionLifecycle.ts`, `useSessionLifecycle.ts`, `App.tsx`, `db/history.ts`, and `strings.ts` stashed (new tests kept), 14 of 35 lifecycle tests fail (delayed-startup save, StrictMode, visibility flush, beforeunload scoping, dirty-until-own-transaction, upgrade-blocked conflict, pre-startup revision buffering, error status, `flushLatest` no-ops) and the new `durability.spec.ts` e2e fails (no `durability-status` element; the red e2e build used `vite build` alone because typecheck fails under the stash). With the change applied, all pass.

## Changes

- `src/lib/sessionLifecycle.ts`:
  - `DurabilityState` gains `status: 'initializing' | 'saved' | 'dirty' | 'saving' | 'memory-only' | 'error' | 'conflict'` and `durableRevision: number | null`. The session candidate stays a separate field, independent of save status.
  - `observeRevision` buffers `{ session, revision }` unconditionally, including before startup resolves; `startup` processes the buffered revision after readiness instead of dropping it (the delayed-startup drop bug).
  - One debounce window per revision. The snapshot is cloned once per debounce, in `commitObserved`, never per observation; `persist` records `durableRevision` for its own revision only. A superseded save's completion still records its revision as durable (the bytes did land) but the status derives from the newest revision, so newer edits stay dirty until their own transaction completes.
  - Memory outcomes set `mode: 'memory'` with a once-only warning; persistent success clears autosave warnings. Thrown saves surface `status: 'error'` with visible copy.
  - `flushLatest()` persists the latest observed revision immediately, skipping no-ops (already in flight, already durable, pristine empty session). Used for visibility changes and explicit close actions.
  - Startup maps `storageAvailable: false` to `memory-only`, and a new `storageProblem: 'upgrade-blocked'` to `conflict`, each with distinct warning copy.
  - Prune and preference-discovery failures are caught as cleanup failures; discovery still proceeds.
- `src/db/history.ts` (deviation from the plan's file list, see below): `getDb` records why storage is unavailable (`'unavailable'` vs `'upgrade-blocked'` for a `VersionError` on open); `historyStorageProblem()` exposes it; `StartupResult` carries it; the problem resets in `resetHistoryFallbackForTests`.
- `src/lib/useSessionLifecycle.ts`: new effect keyed on `[lifecycle, ready, status]`. While work is undurable it registers window `beforeunload` (preventDefault only; a comment documents that asynchronous unload saves are not guaranteed) and document `visibilitychange` (hidden → `flushLatest`). Once `saved`, listeners are removed. Handlers are defined inside the effect, so registration/removal identity is stable.
- `src/App.tsx`: renders `STRINGS.durability[status]` in a `data-testid="durability-status"` element in the header, hidden during `initializing`.
- `src/lib/strings.ts`: `durability` status copy map (`Saved.`, `Unsaved changes.`, `Saving…`, `Memory only.`, `Autosave problem.`, `Storage conflict.`).
- Tests: `tests/unit/session-lifecycle.test.ts` (status model, pre-startup buffering, pruning/prefs failure survival, conflict, dirty-until-own-transaction with `durableRevision`, `flushLatest` persist + durable no-op, error status + clear after durable save, buffer reference identity), `tests/unit/use-session-lifecycle.test.tsx` (delayed-startup save through the real hook, StrictMode mount-cleanup-mount, visibility flush, beforeunload registered only while undurable with handler-identity check), `tests/unit/app-history.test.tsx` (lifecycle mock carries `status`; Saving and Memory-only rendering), `tests/e2e/durability.spec.ts` (new: place signature, wait for `Saved.`, reload, Resume, identical placement bounds and `Saved.` again).

## Deviations and decisions

- `src/db/history.ts` is modified though the plan's file list omits it. The plan requires "expose storage-unavailable and storage-upgrade-blocked states accurately", but `db/history.ts` collapsed every open failure to a memory fallback with no reason. `VersionError` (a blocked schema upgrade) is now distinguished from other open failures there, and `StartupResult` carries the optional `storageProblem` (optional, so existing `{ candidate, storageAvailable }` literals keep compiling).
- The `conflict` status describes the blocked-upgrade start state. It is accurate while idle; once edits happen, saves fall back to memory and the status moves to `memory-only`, which is the honest current truth. A distinct persistent-conflict recovery flow is not in scope for R04.
- `beforeunload` calls only `preventDefault()`. The plan forbids claiming asynchronous unload saves are guaranteed, so no save is attempted in the unload handler; `flushLatest` runs on `visibilitychange` instead, which covers tab switches and most app switches.
- The hook's leave-protection effect re-registers on `dirty` → `saving` transitions (handler identity changes). The unit test asserts the meaningful invariants instead of an exact count: every registered handler is eventually removed, the last handler is removed once `saved`, and no listener exists after `saved`.
- R04 acceptance's "compare against the prior batch fixture" used a temporary unit bench on the lifecycle (numbers above) plus a full `batch-performance.spec.ts` run, since R04 changes only the autosave path and not the batch path.
