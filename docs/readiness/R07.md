# R07 receipt. Own PDF loading, rendering, and thumbnail resources

- Starting commit: `6bda6fe` (R06)
- Regression observed failing first: not applicable in the usual sense. R07's defects are leaks and races that pass silently, so the evidence below is the new lifecycle suite plus the pre-existing suites staying green. The two assertions that previously could not even run (`pdf.destroy is not a function`) failed as soon as the release path existed, which is recorded rather than hidden.

## Changes

- `src/pdf/render.ts`:
  - `loadDocument` retains the loading task and destroys it when the promise rejects. A parse that never produced a proxy still owns a worker slot and a document handle, and previously both were retained for the life of the tab.
  - `renderPage` is replaced by `startPageRender`, which returns `{ finished, cancel }`. `cancel` cancels the `RenderTask` and awaits settlement, so a new render never writes into a canvas the cancelled one still owns. A cancelled render's rejection is treated as the expected outcome of leaving the viewport; a genuine failure still propagates.
  - `capturePageGeometry` cleans up each page it reads.
  - The module-level unbounded `thumbnailCache` is replaced by a per-document cache with a 24-entry least-recently-used budget. Evicted and released bitmaps are closed. A rejected entry is removed from the cache so a retry after a transient failure is not stuck replaying the same rejection.
  - Thumbnail work runs through a scheduler capped at two concurrent renders, ordered by priority so the visible page and its neighbours are not stuck behind a long document's tail.
  - `releaseThumbnails(documentId)` closes and forgets a document's retained bitmaps.
- `src/lib/files.ts`: `createSessionDocument` releases its metadata-only document in a `finally`, covering the zero-page rejection and the session page-ceiling rejection as well as the success path, and cleans up each page it reads.
- `src/components/editor/PageCanvas.tsx`: uses the cancellation handle and drops the stale-completion canvas clearing. That clearing was the blank-canvas bug: a superseded render finishing late would wipe the canvas that the newer render was already drawing into. Only the render that still owns the canvas may now change its loading state.
- `src/components/editor/PageThumbnails.tsx`: passes the active-page distance as scheduler priority and releases the document's thumbnails on unmount or document change.
- `src/components/PdfScratch.tsx`: migrated to `startPageRender` and destroys the document on the cancelled path.

## Deviations

- `renderPage` was replaced rather than extended. Keeping the old signature alongside a cancellable variant would have left two ways to render a page, one of which could not be cancelled.
- The thumbnail cache is keyed per document inside `render.ts` rather than lifted into a component-owned cache. The bitmap outlives any single `ThumbnailItem` (React remounts and `StrictMode` double-effects reuse it), so ownership belongs with the document, not the component.
- Retained bitmaps are closed when a document is released or evicted, not reference-counted per consumer. A consumer draws its bitmap immediately and is then finished with it, so a per-consumer refcount would add bookkeeping without changing when a close happens. A consumer that needed to hold the bitmap across draws would need the count; none does today.

## What the lifecycle tests prove

- A rejected parse destroys its loading task, and encrypted is still distinguished from corrupt.
- `cancel` resolves only after the render task settled, and a cancelled render resolves rather than rejecting.
- A real render failure still reaches the caller, so cancellation did not turn into blanket error suppression.
- Cancelling before the render task exists still settles.
- Thumbnails cache per document, do not leak across documents, drop rejected entries so a retry succeeds, close everything on release, bound retention and close what they evict, admit exactly two concurrent renders, hand a slot back even when a render fails, and run the visible page ahead of a distant one.
- `createSessionDocument` releases its document on the success path, the corrupt rejection, and the page-ceiling rejection.
- In the browser, rapid zoom, rapid scroll, rapid document switching, and repeated document removal all settle on a canvas that is actually painted, with no page or console errors. The one excluded message is the browser's standing notice that `frame-ancestors` cannot be delivered by a meta tag, which R11 resolves by moving the policy to real HTTP headers.

## Not verified here

The retained-memory plateau was not measured. `docs/pdf-resource-profile.md` describes a repeatable CDP `HeapProfiler` scenario with a 1.5 MiB post-unmount allowance, ArrayBuffer and worker-resource counts, and interleaved baseline/candidate runs. That scenario was not re-run against this change, so "repeated intake, removal, and switching plateau in retained memory" is unproven. The code now makes the leaks structurally impossible (bounded cache, explicit closes, explicit release), but structural reasoning is not the measurement the plan asks for, and this item stays open.
